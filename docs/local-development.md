# Local development

## Prerequisites

- Node.js 20+ and npm 10+
- Expo Go or an Android/iOS simulator
- An Azure SQL database for persistence; local development can omit it and use in-memory state
- Entra External ID app registration for real sign-in; local-only auth bypass is available

## Install and run

From the repository root:

```sh
npm install
npm run build
npm run test
```

Start the API with `npm run dev --workspace @cheeta/api`. For local-only development, copy `services/api/.env.example` to `services/api/.env` and set `DEV_AUTH_BYPASS=true`; this maps requests to one local test user and must never be enabled in production. Without a configured SQL connection, links and snapshots are held in process memory and disappear at restart.

Start the mobile client with `npm start --workspace @cheeta/mobile`. Set `EXPO_PUBLIC_API_URL`, `EXPO_PUBLIC_ENTRA_AUTHORITY`, `EXPO_PUBLIC_ENTRA_CLIENT_ID`, `EXPO_PUBLIC_ENTRA_ISSUER`, and `EXPO_PUBLIC_ENTRA_API_SCOPE` from `apps/mobile/.env.example` (Expo public variables are configuration, never secrets). `entraAuthority` is the External ID authority/base URL used for discovery; the redirect URI scheme is `cheeta`. Configure the app registration for authorization-code flow with PKCE, the API scope, and the generated native redirect URI. The API validates access tokens using the configured issuer, audience, and JWKS URL.

## Azure SQL

Set `AZURE_SQL_CONNECTION_STRING` for the API and run `npm run migrate --workspace @cheeta/api` from the repository root. Migration SQL is in `services/api/db/migrations`. No seed data is created. Production uses Azure SQL plus Key Vault; configure `AZURE_KEY_VAULT_URL` and grant the API's managed identity Key Vault secret read/write/delete permissions. `DefaultAzureCredential` is used by the Key Vault adapter.

## Kalshi read-only link

The mobile app submits the API key ID and private PEM to the API over HTTPS. The API uses the supplied credential only on the server and persists it in Key Vault when configured. Without Key Vault (local development), it is kept only in process memory. Credentials are not placed in SQL, returned by the API, or persisted by the mobile UI. Create/manage Kalshi API credentials through Kalshi's official account tooling; no credentials are generated by this project.

The API currently makes signed GET requests for `/portfolio/balance`, `/portfolio/positions`, and `/markets`; its normalizer supports Kalshi's fixed-point dollar fields and older cents fields. Configure a Kalshi key with the provider's required read permissions (including `read::portfolio_balance`). No order, trade, cancel, or modify operation exists. Kalshi documents balance-specific rate limits (1 request/second for Basic/Advanced tiers and 5/second for higher tiers); avoid rapid repeated dashboard refreshes. The read-only integration tests use generated ephemeral test keys and mocked HTTP responses; they do not prove access to a live Kalshi account or guarantee current account eligibility, endpoint availability, response compatibility, or API limits. Set `KALSHI_API_BASE_URL` only to a trusted official endpoint.

## API routes

- `GET /health` — liveness
- `GET /api/providers` — provider/capability list
- `POST /api/providers/kalshi/link` — validate credentials with read-only requests and sync an initial dashboard
- `DELETE /api/providers/kalshi/link` — unlink the current user's account
- `GET /api/account/dashboard` — refresh and return the current user's normalized account and market data

All `/api` routes require a verified Entra bearer access token except when the explicitly local `DEV_AUTH_BYPASS=true` setting is used outside production.
